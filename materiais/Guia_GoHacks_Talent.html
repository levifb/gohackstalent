2Prompt engineering

No sábado você escreve dois tipos de prompt: os que dirigem o Claude enquanto ele programa e os que ficam dentro do seu produto, que o agente usa para classificar, decidir e responder. Os princípios são os mesmos.

Os princípios (guia oficial da Anthropic)

  1. Seja claro e direto. Imagine um colega competente que não sabe nada do seu projeto. O que ele precisaria saber? Escreva isso.
  2. Diga o porquê. "Responda curto, porque o texto vai num WhatsApp" funciona melhor que "responda curto". Com o motivo, o modelo generaliza para casos que você não previu.
  3. Dê exemplos (few-shot). Dois a cinco exemplos de entrada e saída, variados e com pelo menos um caso difícil. É o jeito mais barato de corrigir um classificador.
  4. Separe as partes com tags XML: <instrucoes>, <politica>, <pedido>, <exemplos>. Assim o modelo não confunde dado com instrução.
  5. Peça uma saída estruturada. JSON com campos fixos, validado no código. Sem isso, o agente não se encaixa no resto do sistema.
  6. Dê uma saída para a dúvida. "Se faltar informação, devolva "acao": "revisao_humana" e o motivo." Isso evita alucinação e mostra o human-in-the-loop para a banca.
  7. Diga o que fazer em vez de só proibir. Melhor "escreva em parágrafos curtos, sem listas" do que "não use markdown".
  8. Quebre tarefas grandes em etapas encadeadas. Classificar, depois extrair, depois decidir, depois redigir. Cada etapa fica testável e você vê onde errou.
  9. Itere com dados. Rode o prompt em todos os casos fictícios, olhe os erros, ajuste e rode de novo. Anote cada rodada no LOG.md.

Modelo de prompt para o agente do produto

Você faz a triagem de reclamações de clientes da [marca], um e-commerce de capinhas.
Seu resultado é lido por um sistema, não por uma pessoa: responda só com JSON válido.

<politica>
- Troca grátis até 7 dias após a entrega se o produto veio com defeito.

</politica>

<mensagem>{texto do cliente}</mensagem>

Decida a ação seguindo a política. Se a mensagem for ambígua ou faltar dado,
use "revisao_humana" e explique o motivo em uma frase.

<exemplos> ... 3 casos, um deles ambíguo ... </exemplos>

Formato:
{"categoria": "defeito|atraso|arrependimento|outro",
 "acao": "trocar|reembolsar|responder|revisao_humana",
 "confianca": 0-1, "motivo": "...", "resposta_ao_cliente": "..."}

3Vibecoding com controle: o fluxo com Claude Code

Vibecoding é deixar a IA escrever quase todo o código enquanto você descreve o que quer. Num hackathon de um dia é o caminho certo. O risco é perder o controle do que foi feito, e a banca vai perguntar como funciona. A regra: a IA digita, você decide e confere.

O ciclo: explorar → planejar → implementar → conferir → commitar

  1. Explorar: peça para o Claude ler os dados e o enunciado e resumir o que entendeu. Corrija o entendimento antes de qualquer código.
  2. Planejar: use o plan mode (Shift+Tab). Ele lê e propõe sem editar nada. Edite o plano (Ctrl+G) até concordar.
  3. Implementar em fatias pequenas e verticais. Primeiro um caso funcionando de ponta a ponta, depois os outros.
  4. Conferir: dê ao Claude algo que passa ou falha, como teste, build, script que compara a saída com o esperado ou captura de tela. "Rode os testes e continue até passar." Peça evidência: o comando e a saída, não só "deu certo".
  5. Commitar a cada avanço. O commit é o seu ponto de restauração e o histórico que a banca vê no GitHub.

Comandos para saber de cor

ComandoQuando usar
EscO Claude saiu do rumo. Pare na hora e redirecione. Vale olhar o primeiro minuto de toda tarefa.

/clearCorrigiu a mesma coisa duas vezes e continua errado? Limpe a conversa e escreva um prompt melhor com o que aprendeu. Uma terceira correção raramente resolve.

/code-reviewRevisão do diff por um subagente que não viu a sua conversa. Faça uma por volta das 15h.
/btwPergunta rápida que não entra no histórico.
CLAUDE.mdCurto: o comando de teste, o comando de deploy e as regras que não dá para ver no código ("dados só de dados/, nunca chamar API real"). Não descreva a estrutura de pastas, porque o Claude lê o repositório sozinho.

O que você confere com os próprios olhos

Pode deixar a IA fazer

  • Leitura de CSV/JSON e boilerplate
  • Testes a partir dos casos que você escolheu
  • README, textos de interface
  • Primeiro rascunho dos prompts do agente
Você confere sempre

Antipadrões que custam o dia

  • Pedir "o app inteiro" num prompt só. Sai muito código que você não entende e um bug no meio que ninguém acha.
  • Colar erro sem contexto em loop. Depois de duas tentativas, pare, leia o erro, use /clear e reformule.
  • Escrever em CAIXA ALTA e IMPORTANTE nos prompts. Os modelos atuais seguem uma linha simples, e a ênfase faz a regra ser aplicada demais.
  • Trocar de stack às 14h. Use o que você já domina.
  • Acrescentar feature depois das 15h20 em vez de polir a demo.

4Agentes: o que a banca quer ver nos 40%

Um agente é um modelo de linguagem que usa ferramentas (funções que você escreve, como buscar pedido, consultar estoque ou enviar mensagem) em um loop até terminar a tarefa. A banca pergunta "faz o trabalho sozinha ou depende de mão humana?". Mostre autonomia no caso comum e controle no caso de risco.

Padrões, do mais simples ao mais autônomo

PadrãoComo funcionaBom para
Cadeia de promptsEtapas fixas: classificar → extrair → redigir. O código controla a ordem.A base de quase tudo. Previsível e fácil de testar.
RoteadorO modelo classifica a entrada e manda para o tratamento certo.Triagem de tickets e e-mails.
Agente com ferramentasO modelo decide qual ferramenta chamar e quando parar.Investigar um pedido, cruzar dados.
Avaliador-otimizadorUm segundo prompt revisa a saída do primeiro e pede correção.Respostas ao cliente, descrições de produto.
Humano no loopBaixa confiança ou alto valor vai para a fila de aprovação.Reembolso, cancelamento. Mostra responsabilidade.

Para um projeto de um dia, o melhor costuma ser cadeia ou roteador com uma ou duas ferramentas e um humano no loop. Já é um agente de verdade, e cada etapa pode ser medida. Um agente totalmente livre é difícil de depurar em 6 horas.

Exemplo de arquitetura (tema provável de e-commerce)

mensagem do cliente
   │
   ▼
[1] classificar  ──► categoria + confiança         (prompt com exemplos, saída JSON)
   │
   ▼
[2] buscar_pedido(id) / buscar_rastreio(id)         (ferramentas: leem os CSVs fictícios)
   │
   ▼
[3] decidir pela política ──► trocar | reembolsar | responder | revisao_humana
   │                         (regra dura no código para o que não pode errar:
   │                          valor > R$ 300 → humano)
   ▼
[4] redigir resposta ──► [5] revisor confere o tom e a política
   │
   ▼
painel: resolvidos sozinhos x enviados ao humano, tempo médio, acerto

Medir é o que separa projeto de demo bonita

  • Monte um gabarito: separe de 20 a 30 casos fictícios e anote à mão a resposta certa. Leva 15 minutos.
  • Rode o agente em todos e calcule o acerto. Ajuste o prompt e rode de novo. "Acerto foi de 70% para 93% depois de acrescentar 3 exemplos" é a frase ideal para o slide e para a sabatina.
  • Escolha um número de negócio: "Hoje cada ticket leva ~8 min. Com o agente, 80% saem em segundos e o time só revisa os 20% de risco." Diga que é estimativa e de onde veio.
  • Você já faz isso nos seus projetos, como o WAPE contra o modelo da empresa e o gabarito da correção de listas. Use a mesma lógica: linha de base, sua solução e a diferença.
Regra dura no código, julgamento no prompt O que não pode errar (limite de valor, prazo legal, dado obrigatório) vai num if no código, não no prompt. O prompt fica com o que exige leitura de texto. Explicar essa divisão na sabatina mostra maturidade de engenharia.

5Engenharia de software para um dia

Ninguém espera arquitetura de produção. Espera-se que funcione na demo, que o código seja legível no GitHub e que você saiba explicar. O mínimo que entrega isso:

Stack: use o que você já domina

OpçãoQuando escolher
React + TypeScript (Vite) + função serverlessVocê já fez o Songe com React 19 e TS. É o caminho para um app bonito publicado na Vercel. A chamada ao modelo fica numa rota /api, nunca no navegador.
Python + StreamlitSe o desafio for mais de dados ou análise. Painel em minutos, deploy no Streamlit Community Cloud. Menos bonito, muito mais rápido.

Pergunte no credenciamento o que é a "infraestrutura de IA do grupo": um endpoint próprio, uma chave da API da Anthropic, ou só o Claude no navegador ou no Claude Code. Isso define como o seu app chama o modelo.

Estrutura que cabe no dia

projeto/
  README.md        o problema, como rodar, o link do app, a métrica
  SPEC.md          persona, dor, fluxo, definição do pronto
  LOG.md           cada erro da IA e o que você corrigiu
  CLAUDE.md        comandos de teste e deploy, regras do projeto
  dados/           CSV/JSON fictícios do desafio (só estes!)
  src/agente/      prompts.ts, ferramentas.ts, pipeline.ts
  src/ui/          telas
  tests/           gabarito.test.ts: roda os 20 casos e checa o acerto

Práticas que valem o tempo

  • Isole o núcleo (o pipeline do agente) numa função pura: processar(mensagem, pedido) → decisão. Testável sem interface e reaproveitável no script de avaliação.
  • Valide a saída do modelo. Faça o parse do JSON com tratamento de erro (zod no TS, pydantic no Python). Se vier inválido, tente uma vez de novo e depois mande para revisão humana. O app não pode quebrar na frente da banca.
  • Guarde em cache as respostas da demo. Salve as saídas dos casos que você vai mostrar. Se a rede ou a API cair no pitch, a demo continua. Diga que é cache.
  • Segredos em variável de ambiente (.env no .gitignore). Repositório público com chave exposta é o erro mais comum de hackathon.
  • Commits pequenos e frequentes, com mensagens que contam a história ("agente classifica 20 casos com 93%").
  • Testes só no que importa: o gabarito do agente e as regras duras. Não gaste tempo testando a interface.
  • Nada de dados reais. O regulamento proíbe e você assina termo de confidencialidade. Na declaração da submissão você afirma que fez tudo no evento, então leve conhecimento e templates na cabeça, não código pronto do projeto.

6Produção e deploy

O link do app é opcional, mas a banca valoriza "funciona de verdade". Deixe o deploy pronto no começo do dia, não às 16h.

Checklist de deploy (treine em casa até sair em 10 min)

  1. Repositório público no GitHub com o primeiro commit às 8h50.
  2. Conecte o repositório na Vercel (ou no Streamlit Cloud). Cada git push publica sozinho.
  3. Cadastre a chave de API em Environment Variables no painel, nunca no código.
  4. Faça a chamada ao modelo numa função de servidor (api/agente.ts). O navegador só chama a sua rota.
  5. Abra o link numa janela anônima. Precisa abrir sem login nenhum.
  6. Abra no celular também. A banca pode abrir o QR Code.

O que costuma quebrar na hora

SintomaCausa e correção
Funciona local, quebra no arVariável de ambiente não cadastrada na Vercel, ou caminho de arquivo relativo. Leia os logs da função no painel.
Erro de CORSO front chamando a API do modelo direto. Passe pela sua rota /api.
Função passa do tempo limiteVárias chamadas em sequência. Rode os casos em lote no build ou use cache, e mostre um ao vivo.
Tela brancaErro de build ignorado. Rode npm run build localmente antes do push.

Plano B obrigatório

  • Capturas da tela ou um GIF da demo dentro do PDF dos slides.
  • Modo demo com respostas em cache, se a API falhar.

  2. Ponta a ponta feio antes do almoço, e deploy também.
  3. Agente = etapas + ferramentas + humano no caso de risco.
  4. Gabarito de 20–30 casos. Acerto medido, prompt ajustado, número no slide.
  5. LOG.md de cada erro da IA. Vale nota, alimenta o relatório e responde a sabatina.
  6. Regra dura no código, julgamento no prompt, JSON validado.
  7. Duas correções falharam? /clear e um prompt melhor.
  8. Freeze às 15h20, vídeo de plano B, submissão às 16h10.
  9. Chame mentor cedo e aceite o feedback: são 20% da nota.
